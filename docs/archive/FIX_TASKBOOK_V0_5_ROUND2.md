## A. 环境事务必须在失败时停止操作【P1】

位置：EnvironmentTransaction.cs，UserEnvironmentTransaction、CheckAndRecoverDanglingTransactions、SaveWal、Dispose。

### 已确认缺陷

- WaitOne(3000) 返回 false 或抛异常后，代码仍恢复旧事务并修改用户环境。
- 窗体启动调用的恢复入口没有取得事务锁，可以恢复另一个仍在运行的事务。
- Local 前缀锁无法覆盖同一用户不同 Windows 会话；用户名不是稳定的用户身份标识。
- SaveWal 吞掉写入失败，调用方继续修改注册表。
- 日志更新先删除旧文件再移动新文件，存在丢失恢复记录的窗口。
- 构造过程中部分写入失败时，即便回滚失败也删除日志；构造抛异常后还可能遗留锁资源。
- 恢复失败、日志损坏或未解决事务被吞掉，后续新事务可能覆盖旧记录。
- Dispose 内持久化错误可能阻断锁释放；已恢复项的状态没有在恢复处理中正确使用。

### 修改要求

1. 所有恢复、创建事务和修改日志操作受同一把锁保护。锁按当前用户 SID 隔离，并考虑跨会话。权限不足或超时必须返回明确失败，禁止继续写环境。
2. 正确处理 AbandonedMutexException：依据实际锁所有权执行恢复，确保每条退出路径都释放所持锁和句柄。资源释放放在 finally 中。
3. 启动恢复入口与事务构造入口共用同一套加锁和恢复机制，避免重复获取非预期的锁层级。
4. 修改任何变量前，必须成功保存完整恢复日志。持久化失败应抛出或返回明确错误，保证环境写入次数为零。
5. 日志使用可靠落盘和原子替换；不得删除有效旧日志后再尝试移动。按实际目标框架采用可用的磁盘刷新 API；不要把普通 Flush 自动等同于崩溃持久性保证。
6. 正常恢复、部分写入失败回滚、启动恢复均采用 Compare-and-Restore。外部修改不覆盖，记录明确的冲突结果；不能把冲突默默描述成已恢复原值。
7. 单项恢复失败继续尝试其他项，保留未解决记录。只有全部项已恢复或按明确冲突策略处理后才允许单文件删除日志。
8. 恢复失败或日志损坏时，不得开始新事务覆盖旧记录。报告问题并保留可诊断资料。校验日志版本、变量范围和字段完整性，不能盲目按任意损坏记录写环境。
9. 检查 LauncherService 的宽泛 catch：事务初始化、恢复或日志失败不能被误当成 COM 激活失败，然后静默降级并显示成功。区分环境事务错误与激活错误；恢复失败须显式报告。
10. 不把锁、Compare-and-Restore 或日志描述为完全隔离：外部程序不受该锁约束，比较写入不是跨程序原子操作，其他进程可能已继承临时环境。

### 必须有的隔离测试

采用最小可替换环境存储、日志存储与锁接口或等价测试钩子，不引入复杂依赖注入框架。模拟生产环境行为，不直接操作真实用户变量或生产日志目录。

- 锁超时：没有恢复、日志覆盖或环境写入。
- 持锁期间第二个恢复请求不能提前恢复活跃事务。
- 废弃锁被正确接管，并完成恢复或报告失败。
- 首次日志写入失败：没有环境写入。
- 第 N 个变量写入失败：已写项被恢复；恢复失败项保留日志。
- 外部改值：恢复不覆盖外部值，并可见地记录冲突。
- 日志更新、日志删除失败：可重试且不遗失未恢复信息。
- 日志损坏、未知版本、非法字段：拒绝新事务覆盖，不执行任意环境写入。
- 构造失败及 Dispose 失败后锁资源仍可再次取得。
- 恢复失败不会被 LauncherService 降级逻辑掩盖为正常成功。

## B. 不允许退回按名称关闭进程【P1】

位置：LauncherService.cs，FindMatchingTargetProcesses、CloseExistingInstances。

### 已确认缺陷

无法读取候选进程路径时，只因目标安装类型为 StorePackage 就加入匹配列表。另有 StartsWith(InstallDirectory) 未检查路径分隔边界，会把相似目录前缀当作同一目录。

### 修改要求

- 优先精确匹配规范化可执行路径；如必须匹配目录，验证完整目录边界，不接受 ChatGPT-other 等前缀相似路径。
- 路径不可读时，只有通过实际包身份等可靠证据核实后才能匹配；无法核实时排除并报告，不能仅凭名字关闭。
- 强退前身份核实与授权条件必须成立；promptForceKill 为空不能被解释为已同意强退。
- 释放未使用的 Process 对象；不要扩大可终止进程范围。

### 测试

将身份判断抽为可纯测试的逻辑，覆盖精确匹配、相似目录前缀、路径不可读、包身份不符、身份未知和缺少强退确认回调。测试不得结束真实客户端。

## C. 保存失败必须保留旧配置并反馈【P1】

位置：SettingsStore.cs 的 Save；Program.cs 的 SaveSettings、LaunchChatGPT、CreateShortcut。

### 已确认缺陷

- File.Replace 的宽泛 catch 会先 File.Delete(targetPath)，随后移动失败导致原配置丢失。
- 备份清理失败也落入同一个 catch，可能误触发对已经写好的目标文件的删除。
- SaveSettings(false) 不报告失败，保存并启动和创建快捷方式仍继续显示成功。

### 修改要求

- 已存在配置使用安全替换；替换失败保留旧文件并返回失败，禁止删除原文件作为回退。
- 将提交、备份清理、临时文件清理分开。清理错误不能触发回滚删除已经提交的新配置，应准确描述“保存完成但清理失败”等结果。
- 不存在配置时使用安全创建路径；并发冲突明确失败，不覆盖未知的新文件。
- SaveSettings 返回可判断结果；所有调用者处理失败。“保存并启动”保存失败后应停止启动并显示原因；创建快捷方式之前保存失败也应停止，不能显示整体成功。
- 校验输入时不要默默保留旧端口再声称保存了用户输入。技术术语如“原子落盘”从普通用户提示中移除。

### 测试

测试配置路径完全独立于用户设置。覆盖正常保存、原文件被占用或模拟替换失败、移动失败、备份清理失败、首次创建冲突、非法端口、保存失败后不会调用启动器或快捷方式创建器。验证失败前后的旧配置字节一致。

## D. 时区输入不可静默变成 UTC【P2】

位置：TimezoneHelper.cs；对应 Program.cs 输入、预览和启动错误处理；NetworkProbeService.cs 的偏移字段解析。

### 已复现缺陷

- ParseOffset("-18000") 返回 -18 小时，作为秒数应为 -5 小时；未锚定正则先匹配了数字前缀。
- MapUtcOffsetToPosixTz("UTC+12:45") 返回 "UTC"，把不支持值静默改成零偏移。
- UTC+09:30 映射 Australia/Adelaide，固定偏移被转换为可能随夏令时变化的城市时区；UTC-03:30 同样存在季节变化问题。
- IANA 输入没有有效性验证；错误值可能继续传给客户端。

### 修改要求

1. 区分 API 的秒数偏移和用户的 UTC 文本；优先使用不同解析入口，避免纯数字单位歧义。
2. 用户格式完整匹配，检查小时、分钟范围；拒绝尾随垃圾字符、分钟溢出等输入。
3. 固定偏移不能映射为带季节变化的城市来假装固定时区。若目标运行时无法可靠支持某种偏移，明确标为不支持并阻止使用；GeoIP 展示仍应支持分钟精度。
4. 无效或不支持值不得返回默认 UTC 或洛杉矶以掩盖错误。通过结构化结果或明确异常传递到 UI；预览和实际启动共用同一校验逻辑。
5. IANA 输入按明确支持集合或可验证的时区数据源校验。探测返回的区域若不在支持范围，应保留展示并提示，不能自动将其当作已支持。
6. 保留 TZ 关闭语义及旧配置兼容，旧配置含不支持值时明确提示用户修正，不悄悄变更。

### 测试

- 秒数：28800→+08:00，-18000→-05:00，0→00:00。
- 用户偏移：UTC-8、UTC+05:30、UTC+05:45、UTC+09:30、UTC-03:30、UTC+12:45；分别验证解析结果和转换支持状态，不把两者混为一谈。
- 非法值：UTC+08:99、带垃圾前后缀、越界值、未知 IANA 名称。
- 不支持值不会被转换成 UTC，也不会进入启动流程。
- 任何保留的固定偏移实现检查冬夏两个日期，保证固定语义；无法验证的运行时支持明确标注未验证。
