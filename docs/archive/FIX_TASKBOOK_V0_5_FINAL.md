## 任务一：拒绝缺失必要字段的恢复日志【P1】

### 位置与复现

EnvironmentTransaction.cs：EnvVariableRecord、EnvTransactionLog、DeserializeLog、RecoverDanglingTransactionsLocked。

在模拟环境中设置 TZ=temporary，提供下列日志：

```json
{"version":1,"transaction_id":"broken","variables":[{"key":"TZ","original_value":"original","injected_value":"temporary"}]}
```

当前结果：Success=true、环境写入一次、模拟 TZ 被删除。缺失的 existed 被反序列化为 false，代码将其当成变量原来不存在。该日志还缺少 timestamp，事务 ID 格式也未被校验。

### 修改要求

1. 在任何恢复写入前，完整验证整个日志。不得边检查边恢复，后面的非法记录不能导致前面的记录已被修改。
2. 区分字段缺失与合法默认值：existed=false 是合法状态，但缺少 existed 不是；injected_value=null 可合法表示清除变量，不能被当作字段缺失。
3. 可以使用 DataMember.IsRequired、专用读取 DTO、字段存在性记录或等价的标准 JSON 机制；不要退回 Regex 解析。
4. 明确校验并记录恢复日志格式约定：版本、事务 ID、时间戳、变量列表、记录、键及原值/存在状态。校验事务 ID 格式、可解析时间和字段一致性；例如 existed=true 时 original_value=null 不应被接受为可安全恢复记录。
5. 保留允许变量列表、大小写不敏感重复键检查和空记录拒绝。键的验证与实际使用必须一致；不要验证 Trim 后的键却写入未规范化的另一个键，建议直接拒绝前后空白键。
6. 不把缺失的 restored 自动解释为可执行状态。明确哪些字段是恢复必需字段，哪些兼容旧日志可选；采用既有写入器产生的真实完整日志作为兼容样本。
7. 不为严格校验无必要地升级格式版本；若确需升级，提供完整旧日志的安全兼容路径。无从确定原始状态的日志应保留并返回失败，禁止猜测值恢复。
8. 非法日志不得触发环境写入、删除原日志或新事务覆盖。错误信息应说明字段问题，不显示可能含代理凭据的值。

### 必须补充的测试

- 原始复现：整份日志被拒绝，环境写入次数为零，TZ 保持 temporary，日志字节不变。
- 分别只缺 existed、injected_value、original_value、timestamp 等必需字段，避免一个测试因最前面的错误被拒绝就误以为覆盖了全部校验。
- existed=false 与合法 null 值的完整日志可正常恢复。
- existed=true 且 original_value 为合法字符串的完整日志可正常恢复。
- existed=true 与 original_value=null 等矛盾状态被拒绝。
- 非法事务 ID、非法时间、重复键、空记录、空白包裹键被拒绝。
- 第一条记录合法、第二条记录非法时，整份日志零写入。
- 既有版本写入器生成的完整日志仍可读并正确恢复。

测试使用内存环境、内存日志；修改现有测试中随意填写的事务 ID 和时间字段，使有效样本符合真实格式，不得放宽生产校验来迁就测试。

## 任务二：将外部改值冲突传到启动结果和界面【P2】

### 位置与复现

EnvironmentTransaction.cs：TransactionRestoreResult、Restore；LauncherService.cs：Store 启动分支与 LaunchResult；Program.cs：启动结果显示。

在模拟 PackagedAppActivator 中将模拟 TZ 改成 external 并返回 PID。底层 Compare-and-Restore 正确保留外部值且统计冲突，但 LauncherService 仍返回普通成功和“环境已恢复”，没有显示冲突。

### 修改要求

1. 保持外部改值不覆盖的策略。冲突不等于恢复写入失败，也不应反过来声称全部恢复原值。
2. 将冲突数量或明确警告状态传到 LaunchResult。优先使用结构化字段（例如警告级别、冲突数量），不要让 UI 靠字符串 Contains 判断状态。
3. 客户端已启动且只有冲突时，保留准确的启动结果和 PID，明确展示“客户端已启动；发现 N 项外部修改，已保留”。可将 Succeeded 保留为启动成功，并附警告，避免错误描述为客户端启动失败。
4. UI 使用可见警告状态，避免普通绿色“环境全部恢复”提示。恢复失败仍按现有错误分支报告，不降级为普通冲突警告。
5. 同步 ProcessStatus、EnvironmentAdoptionStatus、Summary 和 ErrorMessage 的语义，避免一个字段提示冲突、另一个仍保证全部恢复。
6. COM 失败但恢复阶段存在冲突时，也保留两方面事实：启动失败与外部修改被保留。
7. 不改变“客户端实际采用环境配置仍未验证”的说明，不把恢复成功当作注入采用成功。
8. 如 AllRestored 当前表示“全部已处理（含冲突）”，澄清名称或增加区分字段，避免上层把它误读为全部恢复原值。

### 必须补充的测试

- 模拟激活成功且外部改值：PID 正确、外部值保留、冲突数量正确、最终结果有警告、面向 UI 的文案不宣称全部恢复原值。
- 模拟激活成功且无冲突：正常成功状态不变。
- 模拟激活成功且恢复写入失败：保持错误状态，不当成只有冲突。
- 模拟 COM 失败且有冲突：错误信息体现启动失败，同时保留冲突说明。
- 警告文案不包含代理凭据或完整环境变量值。

所有激活测试使用现有 PackagedAppActivator 接缝，禁止真实启动客户端。
